When Approval Stops Being Authorization

October 2026 · Krushna Dash

At IBM, I worked on safeguards for an ML-assisted vulnerability pipeline built with watsonx and Granite, Mend, GitHub, and Jira. The pipeline processed findings and proposed fixes. My part of the problem lived around those fixes: deduplication, approval-gated pull requests, safe retries, and audit logs.

I kept getting stuck on the time between approval and execution. A reviewer signs off on one patch. By the time an agent acts, the repository may have advanced, a dependency may have changed, or the agent may have generated a different diff. The approval might have expired too. The tool can still apply a patch, but which patch did the reviewer actually authorize?

Authorization drifts

Lapse is the harness I am building to measure that gap. It tracks whether a coding agent stays inside the scope a reviewer approved. An authorization record binds a task to a specific diff, target revision, file scope, and live grant. A change to any field invalidates the old decision.

Many pipelines store approval as a Boolean on the task: approved once, permitted later. That representation throws away what the reviewer saw. A new patch hash points to different code. A new base commit changes the state that code will enter. An expired grant changes the permission itself.

Paired interventions

The evaluation uses paired synthetic remediation episodes. Both runs begin with the same fictional maintenance task, patch proposal, and review decision. Before execution, one run receives a single intervention. The grant might be revoked or expire under a virtual clock. The patch hash, base revision, or file scope might change. Some pairs introduce a duplicate retry.

Everything else stays fixed. If the agent behaves differently, I can trace that difference to the intervention instead of a new prompt or repair. I use basin-level error analysis for a similar reason in my spatiotemporal ML work at UT Austin’s Center for Space Research. An average can look fine while one narrow failure keeps repeating.

A deterministic policy oracle tracks task state, capability, proposed action, and permission separately. The runner logs the agent’s request, the simulated tool’s response, reapproval requests, successful repairs, and duplicate effects. I score an unauthorized request that gets blocked differently from an unauthorized repository change. Blanket refusal also fails the task, even when it stays inside the boundary.

Binding approval to change

The local prototype is written in Python. It has typed event schemas, fixture validation, a deterministic episode runner, pytest coverage, and a CLI that emits JSONL traces and summary figures. The planned comparison ranges from capability-only execution to execution-time rule checks and grants bound to exact patch hashes and repository versions. Version-pinned model-agent runs come next.

AuthorizationBench and the Agent Action Boundary Benchmark ask broader questions about agent authorization. Lapse focuses on multi-stage software remediation, where time and repository state sit between a human decision and the eventual tool call.

A tool definition says what an agent can do. It says nothing about the exact change a person reviewed or how long that review should hold. Lapse puts those details into the experiment.
