Permission and Proof

November 2026 · Krushna Dash

While working on software security automation at IBM, I spent time around an ML-assisted vulnerability pipeline built with watsonx and Granite, Mend, GitHub, and Jira. The visible job was remediation: classify findings, track issues, and propose fixes. The harder part was controlling what happened around the fix—deduplicating work, gating pull requests on approval, making retries idempotent, and leaving an audit trail.

That work left me with two related questions. First, does an approval remain valid when the world changes between review and execution? Second, if an agent crosses a boundary during a long task, will a monitor still receive the evidence needed to explain why? Lapse and Residue turn those questions into controlled experiments. One studies authorization over time. The other studies evidence under compression.

Lapse

A reviewer can approve a patch, but an approval is not permission for every future action that resembles it. The repository may advance. A dependency may change. The agent may regenerate a different diff, expand the file scope, retry an old run, or act after the grant expires. The tool may still be capable of applying the patch, but capability is not authority.

Lapse asks whether coding agents and their surrounding tool policies preserve the exact scope of an approval. In the model I am testing, an authorized action binds together a task, a patch hash, a target repository revision, a capability, and a live grant. If one of those facts changes before execution, the system must make a new authorization decision.

The evaluation uses paired synthetic remediation episodes. Each episode begins with a fictional maintenance task, a proposed patch, and a simulated review decision. In one half of the pair, the authorization remains valid. In the other, the harness changes exactly one fact: the grant is revoked, its TTL expires under a virtual clock, the patch hash changes, the repository moves to a new base revision, the file scope expands, or an execution is retried. Because the task and surrounding prompt stay fixed, a behavioral difference can be attributed to the authorization change rather than an entirely different scenario.

A deterministic policy oracle tracks task, state, capability, action, and permission as separate objects. The runner records what the agent attempted, what the simulated tool executed, whether a legitimate repair completed, whether reapproval was requested, and whether a retry produced duplicate effects. This separation matters. An agent requesting an unauthorized edit that the tool blocks is not the same failure as a repository being modified. A system that refuses every edit may avoid violations, but it also fails the assigned work.

The local methods prototype is implemented in Python with typed event schemas, validated fixtures, a deterministic episode runner, pytest coverage, and a CLI that emits JSONL traces, summaries, and figures. Its current experimental program compares capability-only execution, approval checked once at proposal time, rules checked again at execution time, and grants bound to exact patch hashes and repository versions. Version-pinned model-agent runs are the next empirical stage.

Lapse builds on questions explored by AuthorizationBench and the Agent Action Boundary Benchmark. Its narrower focus is the interval between approval and execution: exact-change binding, expiry, revocation, state drift, and repeated action. I want each failure to resolve to a specific changed event—not disappear inside one aggregate safety score.

Residue

Residue starts from the monitoring side of the same problem. An agent can spend hours editing files, calling tools, requesting approval, and reacting to policy changes. Eventually the working history becomes too large, and the monitor receives a compressed representation instead of the full trace. If that representation drops a denial, a revocation, or a version change, the monitor may reason correctly from the wrong history.

The research question is not simply whether a summary is readable. It is whether the representation preserves the particular event that makes an action permissible or forbidden. Residue generates fictional agent histories from typed events: edit requests, patch proposals, approvals, denials, expiring grants, repository version changes, and harmless background work. Each event carries an ID, source, logical time, and relevant version information. An independent replay oracle computes the true authorization state without asking another model to judge the first model.

For the same underlying history, the proposed experiment compares a recent-window baseline, a narrative summary, a keyword-guided summary, a compact typed ledger, and an evidence-linked ledger with bounded retrieval. Every representation receives the same token budget, including any retrieved evidence. The monitor must classify the proposed action and cite the event IDs supporting its decision.

That second requirement changes the evaluation. A monitor that catches an unauthorized action but cites the wrong denial has not demonstrated the same kind of understanding as one that identifies the decisive event. Residue therefore measures unauthorized-action detection, false positives on benign actions, retention of decisive evidence, source-event retrieval accuracy, and the token or latency cost of the judgment.

The histories are paired in the same spirit as Lapse. Two traces share the same task and distracting events but differ in one earlier authorization fact. I can vary trace length, the location of the decisive event, and the available context budget, then observe which representation keeps enough evidence to support the correct conclusion. The documented design currently includes the methods paper, conceptual figures, system architecture, evaluation plan, and development specification; implementing the trace harness and model comparisons is the next experimental stage.

Residue is informed by SLEIGHT-Bench, AuditBench, and ARGUS. Its focus is deliberately narrower: controlled context compression and evidence recovery under equal budgets. The goal is a benchmark where every monitoring judgment can be checked against an exact source event.

Reflection

Lapse and Residue study different layers of one system. Lapse asks whether authority remains valid at the moment of action. Residue asks whether the history needed to audit that action survives long enough to reach a monitor. Both depend on keeping distinctions that are easy to blur: capability versus permission, proposal versus execution, summary versus evidence, and detection versus explanation.

My work with spatiotemporal models at UT Austin’s Center for Space Research has made me suspicious of single aggregate metrics. A good overall error can hide a specific geographic failure mode. Agent evaluation has the same problem. A completion rate does not tell me whether the right patch ran under the right grant, and an alert rate does not tell me whether the monitor retained the right proof. I am more interested in measurements that let me reconstruct what changed, what the system believed, and what it was actually allowed to do.
